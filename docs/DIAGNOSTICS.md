# Локальный диагностический журнал

Журнал доступен с `0.1.0-dev.9`: **Inspector → Diagnostics → Download diagnostic log**. Кнопка доступна и в пустой студии, когда проект не удалось открыть. При ошибке сначала выгрузить журнал, затем пробовать повторный расчёт/перезагрузку. Удалять данные сайта для диагностики не требуется.

JSON содержит версию приложения, build ID, время выгрузки и события с `sessionId`, `sequence`, UTC timestamp, elapsedMs, уровнем и details. Каждая новая загрузка страницы получает новый session ID. Worker-события связываются через workerId, engine, requestId, projectId, revision и engineVersion; motion-события дополнительно содержат seek epoch, диапазон запроса и покрытие по рукам. Ошибки сохраняют code, message, retryable и доступный stack.

Записываются создание Worker, запросы и ответы analyze/replan/sample/export, переходы стадий расчёта, непрерывность покрытия, truncation/continuation, сбросы и ошибки motion, Play/Pause/Stop/seek/скорость, подготовка и смена аудиовыхода, буферизация, режим интерфейса, статусы сохранения/открытия, ошибки браузера и ресурсов, online/offline и visibility. У каждого ответа может быть durationMs, если запрос отправлен через общий клиент. Каждый кадр и каждая нота не журналируются.

Исходные MIDI-байты, аудио, SF2/SF3 и массивы поз в журнал не включаются. Сообщения и stack могут содержать имена ресурсов и пути исходников. Журнал хранится локально и автоматически никуда не отправляется; Download создаёт обычный файл для передачи разработчику.

## Хранение и ограничения

- Кольцевая история: до **2,000 событий** и **500,000 символов компактного JSON**, что наступит раньше; старейшие записи удаляются.
- Ключ `pianomotion.diagnostics.v1` в localStorage отделён от музыкальных проектов в IndexedDB. Предыдущая сохранённая история подхватывается при запуске.
- Обычные события сохраняются пакетно с задержкой до одной секунды; ошибки сохраняются сразу. При скрытии/закрытии страницы выполняется дополнительный flush.
- При запрете хранилища или quota error журнал остаётся в памяти и доступен для Download. Такая история не гарантируется после перезагрузки. Сбой логирования не прерывает музыкальную операцию.
- Clear diagnostic log очищает только журнал. Проекты, MIDI, банки и настройки не удаляются.
- Несколько одновременных вкладок имеют разные session ID, но общий ключ истории: при записи действует последнее сохранение вкладки. Для точной последовательности сбоя выгружать журнал из затронутой вкладки; это не централизованный журнал всех вкладок.

## Как искать причину

Для `Motion Worker returned an incomplete window without a continuation point` найти `motion.error` с code `MOTION_COVERAGE_INCOMPLETE`. По requestId проверить предшествующие `worker.request` и `worker.response`: совпадают ли project/revision, каковы requested start/end, coverageStart/coverageEnd, truncated и continuation. Затем сопоставить `motion.reset`/seek epoch и `transport.seek` — старый ответ не должен менять новую сессию.

В исправленном дефекте Native строковая сортировка ставила `10` раньше `8.75`. Ответ заявлял неполное покрытие с началом 10 и концом 9.9167, хотя запрос был 8.75–12.75 и truncated=false. Numeric tuple sorting устраняет причину; guard неполного покрытия сохранён, ошибка не маскируется повтором без продвижения.

Исходники: `apps/client/src/diagnostics/eventLog.ts`, общий `m1WorkerClient.ts`, `motionStreamController.ts`, `audio/transport.ts`, App/Player. Проверки охватывают ограничение памяти, безопасные payload, восстановление между сессиями, отказ persistence, корреляцию Worker, реальную ошибку браузера → reload → Download и журнал настоящего Native playback.
