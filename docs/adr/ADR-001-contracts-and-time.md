# ADR-001: Browser contracts, time, and derived results

Date: 2026-10-13  
Status: M0 implementation decision; the separate page-shell smoke test does not exercise these contracts.

## Context

The desktop model crosses between MIDI parsing, a performance scheduler, pianist profiles, and hand poses. Python object identity (`id(note)`) is used internally for maps and cannot identify a note after JSON serialization or a Worker boundary. Distinct MIDI note events can share pitch and timestamps, so their identity cannot be reconstructed from musical values alone.

The web boundary therefore uses versioned JSON DTOs with Zod runtime schemas. The package rejects unknown fields; a format change must add an explicit schema migration instead of silently dropping information.

## Decisions

`SongDocument` is the editable, revisioned source. Every note has a unique stable `noteId`, every track a unique `trackId`, and notes refer to tracks by ID. An importer creates IDs for source notes and retains them when editing or saving. Two notes may have the same pitch, start, and end; they remain separate notes. If normalization folds source notes together, the normalized note may retain multiple opaque `sourceNoteIds`; no ID is derived from pitch/time, and source identities are not guessed from object identity. `trackId` identifies the decoded instrument track corresponding to desktop `Note.track` / `TrackInfo.index`; raw SMF track, channel, and event ordinals are optional because the current desktop loader does not preserve that mapping consistently. Those optional locators must be populated only by an importer that actually observes the raw events.

Pitch uses the MIDI note number (the piano range is 21–108), velocity and controller values use MIDI's 1–127 and 0–127 ranges, general-MIDI program is 0–127, and MIDI channels and source track indexes are zero-based. `instrumentIndex` is the decoded instrument index used by the desktop model. Optional `Note.sourceEvent` ordinals are zero-based event order within that raw MIDI track, not byte offsets. `TempoChange.eventOrdinal` and `PedalControl.eventOrdinal` instead preserve normalized document-array order for equal-time events; they do not claim to be original SMF event ordinals. Profile creation/modification times are Unix seconds. Resource byte lengths count octets; SHA-256 values are lowercase hexadecimal.

Times in source documents, tempo maps, pedal controls, and performance events are finite seconds from the beginning of the source song. Source note starts are at least zero and each end is strictly after its start. The `durationSeconds` covers all notes. Raw MIDI bytes are separate package resources described by a path, media type, byte length, and SHA-256; the note/document DTO never embeds the binary data. A source event mapping is a locator into those original bytes, not a replacement for them.

Transport position is a separate quantity. Desktop `common.LEAD_IN` permits a playhead at -2 seconds before the first source event. `TransportTimeSchema` accepts that lead-in, while note and performance event schemas do not. Playback advances across `(t0, t1]`; a seek marks notes already sounding as active and does not retrigger them.

Performance events at the same time are ordered by **release → pedal → press**, matching `common.Transport.update`. Event arrays must already be sorted by time and that priority; consumers process equal-priority events in their serialized array order. Each fingering plan assigns every normalized note exactly one explicit disposition: played (finger 1–5), glissando (no finger), or unplayable (no finger), and its hand must match the normalized source note. Explicitly marked same-hand notes follow `glissando.explicit`: runs with at least two marked notes and no more than 0.5 seconds between marked onsets must all use the glissando disposition; a solitary marked note remains eligible for ordinary fingering. Unmarked notes may also receive a glissando disposition when the engine detects a run. The performance plan uses the timings the hands actually play, including rolled chords and early releases; it must include each played/glissando note once and omit unplayable notes. This makes the desktop's omitted sixth chord note explicit rather than silently dropping it. Pedal controls in the source document retain MIDI values 0–127. Derived performance pedal events must exactly match the ordered source-control stream after thresholding each controller at `value >= 64` to 127 and lower values to 0, with an initial state of 0 and unchanged states omitted; this prevents missing or fabricated pedal changes.

`PianistProfile` is independently revisioned. Every derived plan includes the source `projectId`, `inputRevision`, `profileId`, `profileRevision`, and `engineVersion`, including performance plans that consume a fingering plan. Worker requests carry full versioned document/profile inputs and the expected engine version; embedded upstream plans must match those document, profile, engine, and plan-ID values. Fingering and performance plans validate note references; performance plans point to the exact fingering plan they consume. A response may only be applied if its `requestId`, operation, project, document revision, profile revision, and engine version still match the outstanding request and current editor state. A stale response is discarded.

Derived-result cache keys consist of project ID, document revision, profile ID/revision, engine version, operation, and a digest of canonical operation parameters. Any edit to song data, imported resources, or relevant profile settings increments the corresponding revision. Cache consumers require exact key equality; old results may be kept as historical data but are never reused for a newer revision. The digest is computed over canonical JSON, not JavaScript object identity.

Motion samples use the named `keyboard-local-inches-v1` frame: x points right along the keyboard from its left edge, y points away from the pianist from the keyboard's front edge, and z points above the key surface. The desktop pose builder emits pixel coordinates plus `ppi` and `front_y`; screen projection is `screenY = front_y - rawY`, so increasing raw y points away from the pianist. The M1 adapter converts each desktop point `(rawX, rawY, rawZ)` to `((rawX - keyboardLeft) / ppi, rawY / ppi, rawZ / ppi)`, using the left edge of the lowest key for `keyboardLeft`. This puts the source key surface at z=0 and retains the desktop depth direction. It must not mirror left-hand coordinates a second time after the desktop pose has flipped them. `layerOrder` sorts whole hands at crossings (larger is drawn on top); both hands may share a layer when no crossing lift applies. Pose-array order is time then left before right, and bone/joint array order retains the within-hand skeleton order. A motion sample's time uses transport seconds so it can represent the negative lead-in without allowing negative source notes.

## Consequences

- JSON inputs are checked at package, request, and response boundaries; semantic references need the document/profile context as well as a shape schema. Progress, cancellation, and Worker lifecycle messages are deferred to M1.
- Schema version 1 has no automatic migration yet. Importers must reject unsupported versions and later add tested migrations before changing persisted shapes.
- Raw source bytes remain independently recoverable and hash-checkable; exact event-level edit/export preservation still requires importer/exporter work.
- The contract describes data and ordering, not algorithm parity or performance. The separate Chromium smoke test checks the page shell only; MIDI handling, audio output, pose conversion, and benchmarks are not claimed tested by this ADR.

## Desktop evidence used

- `midi_loader.Note` stores pitch, source seconds, velocity, instrument index, hand, optional finger, and glissando; `MidiSong` sorts notes and retains raw pedal values separately from thresholded pedal switches.
- `common.Performance` represents actual press/release pairs. `common.Transport.update` sorts equal-time events with release priority 0, pedals 1, and presses 2, across `(t0, t1]`.
- `Pianist` stores anatomy, behavior, skin, and fingering weights. `HandAnimator.pose` produces bones/joints and `ppi` in a keyboard-relative screen layout, with left-hand mirroring and crossing layers applied by the desktop renderer.
